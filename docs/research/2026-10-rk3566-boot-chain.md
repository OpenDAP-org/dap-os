# RK3566 boot chain for OpenDAP OS: research and recommendation

- Date: 2026-10-21
- Scope: a custom Rockchip RK3566 board running OpenDAP OS (Debian trixie, trixie-backports kernel, mainline Linux 7.x, device tree plus overlays applied by the bootloader).
- Constraint from the maintainers: no embedded-style builds (no Yocto/Buildroot/vendor SDK). Use prebuilt artifacts where possible. Build U-Boot only if that is clearly the best option.
- Method: I fetched primary sources on 2026-10-21. Anything I could not confirm against a primary source today is marked **UNVERIFIED**. The web-search quota for this session ran out, so all research was done by fetching known primary URLs directly. `opensource.rock-chips.com` did not resolve (DNS failure) on the research date, so every claim that depends on the Rockchip wiki is marked UNVERIFIED.

---

## TL;DR

- **DDR init is still a closed Rockchip blob for RK3566/RK3568.** Mainline U-Boot has no open-source DRAM training for this SoC: `drivers/ram/rockchip/sdram_rk3568.c` only reads the DRAM size that the blob writes into a PMU GRF OS register. The U-Boot docs explicitly list rk3568 among the SoCs that need `ROCKCHIP_TPL` from rkbin.
- **Mainline TF-A BL31 supports RK3566/RK3568** (platform `rk3568`, upstream since about v2.10). **Debian already ships it prebuilt** in `arm-trusted-firmware` (`/usr/lib/arm-trusted-firmware/rk3568/bl31.elf`, trixie 2.12.1, testing/sid 2.12.16).
- **OP-TEE upstream does not support RK3568/RK3566** (upstream supports rk322x, rv1106, rk3399, px30, rk3506, rk3588, rk3576). The only option is Rockchip's closed `rk3568_bl32_v2.18.bin`. OpenDAP OS does not need a TEE.
- **Debian's `u-boot-rockchip` does not build any RK3566/RK3568 board**, in trixie or sid (only rk3328/rk3399). The reason is that a working image needs the non-free DDR blob.
- **Rockchip's own recommended path is the vendor stack**: U-Boot `next-dev` (based on 2017.09), plus rkbin, plus `make.sh` / `boot_merger` / `trust_merger`. It is built for the vendor 5.10/6.1 BSP kernels and is the wrong fit for a mainline Debian system. Mainline U-Boot docs, which Rockchip engineers contribute to, document a much simpler mainline path.
- **Recommendation (section 6):** build **mainline U-Boot once** from `generic-rk3568_defconfig`, or a small board defconfig derived from it. Feed it the **rkbin `rk3566_ddr_1056MHz_v1.26.bin`** as TPL and **Debian's prebuilt TF-A `rk3568/bl31.elf`** as BL31. Use the **Debian cross toolchain**. Package the single resulting `u-boot-rockchip.bin` as a OpenDAP OS `.deb`, and boot through **extlinux.conf generated by Debian's `u-boot-menu`**, which supports `fdtoverlays`. That is one `make` command of a few minutes, not an embedded build.

## 1. RK3566 boot flow and open/closed status today

### 1.1 Stages

```text
BootROM (mask ROM, closed, in silicon)
  -> searches SPI NOR/NAND, eMMC, SD for an "idblock" at sector 64 (0x8000); falls back to USB MaskROM
  -> TPL  = DDR init            [rkbin blob rk3566_ddr_*.bin, CLOSED]
  -> SPL  = U-Boot SPL          [mainline U-Boot, OPEN] (vendor alternative: rk356x_spl_v1.14.bin, closed)
       loads FIT image u-boot.itb containing:
  -> BL31 = TF-A (EL3 monitor)  [mainline TF-A rk3568, OPEN]  or rkbin rk3568_bl31_v1.46.elf [CLOSED]
  -> BL32 = OP-TEE (optional)   [rkbin rk3568_bl32_v2.18.bin, CLOSED; no upstream port]
  -> BL33 = U-Boot proper       [mainline U-Boot, OPEN]
  -> Linux kernel + DTB (+ overlays) via extlinux / bootstd
```

With mainline U-Boot, binman produces a single `u-boot-rockchip.bin` (idbloader with TPL and SPL, then a FIT with BL31, optional TEE, U-Boot and its DTB). It is written at sector 64 of SD/eMMC (`dd ... seek=64`). A `u-boot-rockchip-spi.bin` is written at offset 0 of SPI flash. Source: U-Boot docs, <https://docs.u-boot.org/en/latest/board/rockchip/rockchip.html> and <https://raw.githubusercontent.com/u-boot/u-boot/master/doc/board/rockchip/rockchip.rst>. Binman layout: <https://raw.githubusercontent.com/u-boot/u-boot/master/arch/arm/dts/rockchip-u-boot.dtsi>, where the `tee-os` node is marked `optional`.

The vendor/legacy layout instead uses `idbloader.img` at sector 64, `uboot.img` at 16384 and `trust.img` at 24576. Armbian still writes `idbloader.img` at 64 and `u-boot.itb` at 16384 for its "spl-blobs" scenario. Source: <https://raw.githubusercontent.com/armbian/build/main/config/sources/families/include/rockchip64_common.inc>. The exact BootROM media search order on RK356x is **UNVERIFIED**: I could not reach the Rockchip wiki `wiki_Boot_option`.

### 1.2 Open vs closed, per stage (as of 2026-10-21)

| Stage | Open-source option | Closed option | Status for RK3566 |
|---|---|---|---|
| BootROM | none | in silicon | closed, unavoidable |
| DDR init (TPL) | **none** | rkbin `rk3566_ddr_1056MHz_v1.26.bin` (and variants `_ultra`, `920MHz`, eyescan) | **blob only** |
| SPL | mainline U-Boot SPL | `rk356x_spl_v1.14.bin` | open is mature |
| BL31 | mainline TF-A `PLAT=rk3568` | `rk3568_bl31_v1.46.elf` | open is usable (see below) |
| BL32 (OP-TEE) | **no upstream port** | `rk3568_bl32_v2.18.bin` | blob only, optional |
| U-Boot proper | mainline U-Boot | vendor next-dev 2017.09 | open is mature |

#### Is DDR init open in mainline U-Boot? No

- The U-Boot Rockchip doc says: "For some SoCs U-Boot sources lack of support to inizialize DRAM. In these cases ... use DDR binary provided by Rockchip rkbin repository as ROCKCHIP_TPL". It names rk3308, rk3528, **rk3568** (`rk3568_ddr_1560MHz_v1.13.bin`), rk3576 and rk3588. Source: rockchip.rst above.
- `drivers/ram/rockchip/sdram_rk3568.c` is about 55 lines. `rk3568_dmc_probe()` reads the SDRAM size from `pmu_os_reg2`, which the blob leaves behind. There is no training code. Source: <https://raw.githubusercontent.com/u-boot/u-boot/master/drivers/ram/rockchip/sdram_rk3568.c>
- Current rkbin RK3566 DDR blobs are at v1.26: <https://github.com/rockchip-linux/rkbin/tree/master/bin/rk35>. They are redistributable: the rkbin LICENSE grants "use, copy, distribute", forbids reverse engineering, and is not DFSG-free. Source: <https://raw.githubusercontent.com/rockchip-linux/rkbin/master/LICENSE>

#### Is mainline TF-A BL31 usable for RK3566? Yes

- TF-A lists "rk3566/rk3568: Quad-Core Cortex-A55" as supported: <https://trustedfirmware-a.readthedocs.io/en/latest/plat/rockchip.html>. Platform code is at <https://github.com/TrustedFirmware-A/trusted-firmware-a/tree/master/plat/rockchip/rk3568>
- The TF-A changelog records "add rk3568 support" in the 2.10 cycle. The changelog fetch returned a date of 2023-04-03, which does not match the usual v2.10 release in Nov 2023, so the exact date is **UNVERIFIED**. v2.15.0 (2026-05-27) adds RK3568 hardening: an early CPU reset "to enable crypto function", and protecting TF-A memory with the DDR firewall. Source: <https://raw.githubusercontent.com/TrustedFirmware-A/trusted-firmware-a/master/docs/change-log.md>
- The U-Boot docs show both choices for rk3568: `BL31=../trusted-firmware-a/build/rk3568/release/bl31/bl31.elf` **or** `BL31=../rkbin/bin/rk35/rk3568_bl31_v1.34.elf`.
- **Debian ships it prebuilt**: `arm-trusted-firmware` contains `/usr/lib/arm-trusted-firmware/rk3568/bl31.elf`. Versions are 2.12.1+dfsg-1 in trixie and 2.12.16+dfsg-1 in forky/sid (migrated 2026-10-10). Sources: <https://packages.debian.org/trixie/arm64/arm-trusted-firmware/filelist>, <https://tracker.debian.org/pkg/arm-trusted-firmware>
- Caveats: Armbian still defaults to the rkbin BL31 (`rk3568_bl31_v1.44.elf`) for rk3566/rk3568 (rockchip64_common.inc). Feature parity of mainline BL31 with the vendor BL31 is **UNVERIFIED**, in particular system suspend-to-RAM and vendor SIP calls such as DDR DVFS, which mainline Linux does not use anyway. **Test suspend/resume on the board if OpenDAP OS needs it.**

**OP-TEE:** upstream `plat-rockchip` flavors are rk322x, rv1106, rk3399, px30, rk3506, rk3588 and rk3576. There is **no rk3568**. Source: <https://raw.githubusercontent.com/OP-TEE/optee_os/master/core/arch/arm/plat-rockchip/conf.mk>. Only the closed rkbin `rk3568_bl32_v2.18.bin` exists (loaded at 0x08400000 per `RKTRUST/RK3568TRUST.ini`). Mainline U-Boot treats TEE as optional. **Recommendation: no BL32 on OpenDAP OS** unless a concrete TEE use case appears.

## 2. What Rockchip itself recommends

- **Rockchip's official SDK path is the vendor stack:** `rockchip-linux/u-boot`, default branch `next-dev`, `VERSION = 2017 / PATCHLEVEL = 09` (<https://github.com/rockchip-linux/u-boot>, <https://raw.githubusercontent.com/rockchip-linux/u-boot/next-dev/Makefile>). It is built with `./make.sh`, which reads `rkbin/RKBOOT/RK3568MINIALL.ini` (for RK3566 the DDR is `rk3566_ddr_1056MHz_v1.26.bin` and the SPL is `rk356x_spl_v1.14.bin`) and `RKTRUST/RK3568TRUST.ini` (BL31 v1.46 and BL32 v2.18). The outputs are `uboot.img`, `trust.img` and `rk356x_spl_loader*.bin`, packed with `boot_merger` / `trust_merger`. Sources: <https://raw.githubusercontent.com/rockchip-linux/u-boot/next-dev/make.sh>, <https://raw.githubusercontent.com/rockchip-linux/rkbin/master/RKBOOT/RK3566MINIALL.ini>, <https://raw.githubusercontent.com/rockchip-linux/rkbin/master/RKTRUST/RK3568TRUST.ini>
- This stack goes with the vendor BSP kernel (5.10/6.1) and Rockchip tooling (`rkdeveloptool`, `upgrade_tool`, `parameter_gpt.txt`). It is **not** designed for a mainline 7.x Debian kernel with a standard extlinux flow. It drags in Android-style partitioning and vendor boot commands, and it is pinned to a 2017 code base with known CVE debt.
- **For mainline, Rockchip publishes the binaries rather than a separate guide.** The rkbin README describes the repo as the home of "SPL/DDR/UsbPlug/BL31/BL32/OPTEE" binaries, RKBOOT/RKTRUST ini files and tools (<https://github.com/rockchip-linux/rkbin>). Mainline U-Boot's `doc/board/rockchip/rockchip.rst` then tells you to take the DDR blob from rkbin as `ROCKCHIP_TPL`, and BL31 from TF-A or rkbin. The rk3568 TF-A port is upstream, and Rockchip engineers contributed it (author attribution **UNVERIFIED**). Rockchip's wiki pages `wiki_U-Boot` and `wiki_Boot_option` historically document both vendor and mainline flows and the partition offsets. **UNVERIFIED today**: the site was unreachable on 2026-10-21.
- Bottom line: Rockchip's *product* recommendation is vendor U-Boot plus rkbin. Rockchip's *upstream* contribution, plus the U-Boot docs, support **mainline U-Boot plus rkbin DDR plus (mainline or rkbin) BL31**, which is what Armbian, Radxa (newer images), Pine64 community distros and Collabora-style upstream work use.

### 3.4 Can a prebuilt binary be reused on a custom board?

A `u-boot-rockchip.bin` embeds three board-specific things.

1. **DDR blob configuration.** The rkbin DDR blob auto-detects DRAM type (DDR3/DDR4/LPDDR3/LPDDR4/4X) and capacity at runtime, so the *same* blob usually works across boards. What can differ is target frequency (pick the 1056 MHz RK3566 blob, or 920 MHz if the layout is marginal), drive strength/ODT, and the debug UART iomux and baud rate. These are patched in the binary with rkbin `tools/ddrbin_tool.py` and `ddrbin_param.txt`, with no rebuild. Source: <https://github.com/rockchip-linux/rkbin/tree/master/tools>, <https://raw.githubusercontent.com/rockchip-linux/rkbin/master/tools/ddrbin_param.txt>. Auto-detection scope is from rkbin docs and common knowledge: **UNVERIFIED** in detail.
2. **U-Boot control DT (OF_UPSTREAM).** This covers the pinmux and controllers for the boot media (SDMMC0, eMMC 8-bit, FSPI), the debug UART (UART2 at 1.5 Mbaud by default), and the regulators and io-domains that SD needs (vccio_sd from the RK817/RK809 PMIC). A reference board's DT may enable a PMIC, PCIe, Ethernet or USB topology that does not exist on your board. Usually that causes probe errors, not bricks, but a wrong SD power or io-domain voltage will stop SD boot.
3. **Boot media and env location**: SD/eMMC at sector 64, SPI at offset 0, and `CONFIG_SYS_SPI_U_BOOT_OFFS=0x60000`.

The safest prebuilt-reuse candidate is a **`generic-rk3568` build**. Its DT is deliberately "Minimal generic DT for RK3566/RK3568 with eMMC, SD-card, SPI flash and USB OTG enabled" (<https://raw.githubusercontent.com/u-boot/u-boot/master/arch/arm/dts/rk3568-generic.dts>, <https://raw.githubusercontent.com/u-boot/u-boot/master/configs/generic-rk3568_defconfig>). Next best is a reference board that the custom board copied (for example a Radxa CM3 or Quartz64 carrier). Even so, nobody publishes a prebuilt generic-rk3568 binary in a distro repo (I found no such package), so in practice you end up building it.

## 4. If we build: minimal reproducible recipe

### 4.1 Inputs (all prebuilt except U-Boot itself)

- Mainline U-Boot release tag (for example `v2026.10`).
- `rkbin/bin/rk35/rk3566_ddr_1056MHz_v1.26.bin`, pinned by rkbin commit and sha256.
- BL31 from Debian `arm-trusted-firmware`: `/usr/lib/arm-trusted-firmware/rk3568/bl31.elf`. Fallback: rkbin `rk3568_bl31_v1.46.elf` if suspend or another feature is missing.
- A Debian toolchain. On an amd64 host: `gcc-aarch64-linux-gnu`. On an arm64 host or chroot: the native `gcc`.
- Build deps (Debian): `build-essential bison flex bc libssl-dev libgnutls28-dev python3 python3-dev python3-setuptools python3-pyelftools python3-cryptography swig device-tree-compiler uuid-dev`. The exact list is from U-Boot's `doc/build/gcc.rst` and Debian's u-boot Build-Depends. **UNVERIFIED** list completeness.

### 4.2 Build (inside a `debian:trixie` container for reproducibility)

```sh
apt-get install -y gcc-aarch64-linux-gnu arm-trusted-firmware <deps above>
git clone --depth 1 -b v2026.10 https://source.denx.de/u-boot/u-boot.git
git clone https://github.com/rockchip-linux/rkbin && git -C rkbin checkout <pinned-sha>
export BL31=/usr/lib/arm-trusted-firmware/rk3568/bl31.elf
export ROCKCHIP_TPL=$PWD/rkbin/bin/rk35/rk3566_ddr_1056MHz_v1.26.bin
export SOURCE_DATE_EPOCH=<fixed>
make -C u-boot CROSS_COMPILE=aarch64-linux-gnu- generic-rk3568_defconfig   # or dap-rk3566_defconfig
make -C u-boot CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)
# outputs: u-boot-rockchip.bin (SD/eMMC, dd seek=64) and u-boot-rockchip-spi.bin (SPI, offset 0)
```

- **Effort:** the build itself takes roughly 2 to 5 minutes on a laptop. Writing the CI container takes about half a day. Adding a board DT and defconfig (if `generic` is not enough: for example a PMIC regulator for SD, Ethernet for netboot, or a non-default UART) takes about 1 to 3 days including bring-up on hardware. Ideally that DT is upstreamed to Linux, after which U-Boot picks it up through `dts/upstream`. Ongoing work is one rebuild per U-Boot release or rkbin bump.

### 4.3 Packaging as a OpenDAP OS `.deb`

Mirror Debian's own `u-boot-rockchip` layout so the tooling feels native.

- `u-boot-dap-rk3566_<ver>_arm64.deb` installs `/usr/lib/u-boot/dap-rk3566/{u-boot-rockchip.bin,u-boot-rockchip-spi.bin}` plus a small `/usr/sbin/dap-u-boot-install` script. The script `dd`s the image to `seek=64` on the boot eMMC/SD (or flashes SPI with `flashcp`/mtd-utils), and it refuses to run if the target is not the boot device.
- Put the package in a **non-free-firmware-style DAP component** and ship the rkbin LICENSE in `debian/copyright`. The binary embeds the redistributable but non-DFSG DDR blob.
- **Do not auto-flash in `postinst`** by default. Make it explicit, or gate it behind a debconf flag. A failed bootloader write is the main way to brick the board, and recovery is MaskROM plus `rkdeveloptool` with `rk356x_spl_loader`.
- Build it in CI from a pinned Dockerfile, and record the sha256 of the inputs (U-Boot tag, rkbin sha, Debian ATF version) in the changelog.

### 4.4 Device tree and overlays

- Mainline U-Boot uses **bootstd**, which scans `extlinux/extlinux.conf`, EFI and boot scripts. extlinux supports `fdt`, `fdtdir` and **`fdtoverlays`**. Overlays are loaded at `fdtoverlay_addr_r` and "applied in the load order to the fdt blob". Sources: <https://raw.githubusercontent.com/u-boot/u-boot/master/doc/develop/distro.rst>, <https://raw.githubusercontent.com/u-boot/u-boot/master/doc/usage/pxe.rst>. This needs `CONFIG_OF_LIBFDT_OVERLAY`, which is enabled on Rockchip defconfigs (**UNVERIFIED** for generic-rk3568: check `.config`).
- **Debian `u-boot-menu` 4.2.4 (trixie)** generates `/boot/extlinux/extlinux.conf` on every kernel install. It supports `U_BOOT_FDT`, `U_BOOT_FDT_DIR`, `U_BOOT_FDT_OVERLAYS`, `U_BOOT_FDT_OVERLAYS_DIR` and `U_BOOT_SYNC_DTBS`. Source: <https://manpages.debian.org/trixie/u-boot-menu/u-boot-update.8.en.html>, <https://packages.debian.org/trixie/u-boot-menu>. This is the most "Debian-native" way to apply the DAP board DT plus overlays with the trixie-backports kernel. Set `U_BOOT_FDT=rockchip/rk3566-dap.dtb` and list overlays in `U_BOOT_FDT_OVERLAYS`.
- Alternatives: a signed FIT (kernel + DTB + overlays as configurations), which is needed for verified boot (section 5), or a `boot.scr` with `fdt apply`. Do not modify the DT in U-Boot env.

### 4.5 A/B boot

- U-Boot `CONFIG_BOOTCOUNT_LIMIT` with the `bootcount`/`bootlimit`/`upgrade_available`/`altbootcmd` env variables. The backend is `CONFIG_BOOTCOUNT_ENV` (counter stored in the U-Boot env, with `ENV_IS_IN_MMC` or `ENV_IS_IN_SPI_FLASH`, a redundant env and `CONFIG_SYS_REDUNDAND_ENVIRONMENT`). This is the standard pattern used by RAUC/SWUpdate/Mender. A RAM/register-based bootcount that survives warm reset on RK3568 (PMU GRF OS registers) is **UNVERIFIED**. Prefer the env backend.
- Implementation: two rootfs partitions (and two `/boot` copies, or `/boot` inside each rootfs). A U-Boot env variable `dap_slot=a|b` selects which partition bootstd scans, or an extlinux entry per slot with `default` set from env. Userspace clears `upgrade_available` and `bootcount` with `fw_setenv` (`libubootenv-tool`, in Debian) after a health check. Also enable the hardware watchdog (`CONFIG_WDT`, the dw_wdt driver) so that a hung kernel increments the count.
- The bootloader itself is not A/B on RK356x. The BootROM can fall back from one idblock copy to a backup (vendor docs mention multiple idblock copies, **UNVERIFIED**). Keep bootloader updates rare and atomic, and keep SPI NOR, if present, as an immutable recovery bootloader.

## 5. Secure boot / verified boot (brief)

- **Hardware root of trust:** RK3566/RK3568 BootROM can verify the first loader against an RSA public-key hash burned into **OTP**. This is set up with Rockchip's `rk_sign_tool` (in rkbin `tools/`) together with the vendor U-Boot's FIT signing flow (`fit-sign.sh` etc. in rkbin tools). Burning OTP is **irreversible**. Details (key size, OTP write procedure, whether the closed DDR blob is covered) are in Rockchip's "Secure Boot" developer guide, which ships with the SDK: **UNVERIFIED** here.
- **Mainline:** U-Boot SPL supports `CONFIG_SPL_FIT_SIGNATURE` (enabled in `generic-rk3568_defconfig`, which binman uses for hashing), and U-Boot proper can verify signed kernel FITs (`CONFIG_FIT_SIGNATURE`). Without the BootROM verifying TPL+SPL, the chain is not anchored in hardware. Whether mainline `mkimage`/binman can produce a BootROM-signed RK3568 idblock is **UNVERIFIED** (I found no doc for it). TF-A v2.15 RK3568 changes (crypto enablement and the DDR firewall) suggest that upstream hardening is ongoing.
- **Practical guidance for OpenDAP OS:** defer hardware secure boot. If tamper resistance is required later, the path is: (a) mainline U-Boot with a signed kernel/DTB/overlay FIT and the public key in the U-Boot DTB, giving software verified boot; then (b) BootROM OTP signing using Rockchip tools on the already-built `u-boot-rockchip.bin` idblock, after validating on sacrificial boards. Moving overlays into FIT configurations is a prerequisite, because extlinux `fdtoverlays` files are not authenticated.

## 6. Recommendation (my recommendation, not a Rockchip statement)

**Use mainline U-Boot, built once in CI from Debian packages, with exactly one closed input: the rkbin RK3566 DDR blob.**

1. **U-Boot:** mainline release (2026.10, then track releases), starting from `generic-rk3568_defconfig`. Add a `dap-rk3566` DT and defconfig only if the board needs PMIC/regulator, network or UART changes for boot. Upstream the board DT to Linux so that U-Boot inherits it.
2. **TPL:** rkbin `rk3566_ddr_1056MHz_v1.26.bin`, pinned by commit and hash, tuned with `ddrbin_tool` if the layout requires it.
3. **BL31:** Debian's prebuilt `arm-trusted-firmware` `rk3568/bl31.elf`. This is open, and it is updated and security-tracked by Debian. Fall back to rkbin BL31 only if hardware tests show a missing feature (for example suspend).
4. **No OP-TEE** (no upstream port; not needed).
5. **Boot flow:** bootstd, then extlinux generated by Debian **`u-boot-menu`**, with `U_BOOT_FDT` and `U_BOOT_FDT_OVERLAYS`. The trixie-backports kernel DTB comes from the `linux-image` package, with the board DT shipped by DAP if it is not upstream yet.
6. **A/B:** `BOOTCOUNT_ENV` with a redundant env plus `libubootenv-tool` in userspace, and the watchdog enabled.
7. **Ship** as `u-boot-dap-rk3566` .deb in a non-free-firmware component, with an explicit install script and no silent `postinst` flashing.

### Why

- **There is no fully prebuilt option.** Debian does not build any RK356x board, because of the DDR blob. Armbian and vendor binaries carry another board's DT and are packaged for their own distros. The vendor stack is 2017-era and BSP-oriented.
- **The "build" is minimal and not embedded-style.** It is one `make` against Debian's toolchain and Debian's BL31, takes a few minutes, and produces one artifact. It needs no SDK, Yocto or Buildroot.
- It matches what the U-Boot docs (which Rockchip contributes to) describe for rk3568, and what Armbian, Radxa (newer images) and Pine64 do. It also keeps the closed surface to the unavoidable minimum: BootROM plus the DDR blob.
- It gives a modern, maintained bootloader (bootstd, extlinux overlays, FIT signing, bootcount) that fits Debian's own `u-boot-menu` and `libubootenv` tooling, which is exactly the OpenDAP OS model.
- **Rejected:** vendor U-Boot 2017.09 + `make.sh` (old, CVE-laden, BSP-coupled, Android-style layout), and reusing a third-party board's prebuilt binary (wrong DT, power and io-domain; fragile; unsupported for a product).

**Open items to verify on hardware:** SD/eMMC/SPI boot with `generic-rk3568`; the DDR blob on the actual DRAM part and frequency; suspend/resume with mainline BL31; `fdtoverlays` application with the trixie-backports kernel DTB; bootcount rollback under watchdog reset; and recovery through MaskROM + `rkdeveloptool`. Nothing in this report has been exercised on the DAP board yet, so this is a **landed research recommendation, not a verified boot chain**.
