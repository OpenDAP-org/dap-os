# DSD512 on the T1

- **Status:** Proposal accepted by the maintainers on 2026-10-22 (ADR 0006 amended). Research findings on the open items are in §5; §3 carries the resulting work outlines.
- **Date:** 2026-10-22
- **Requirements:** OS-020 (bit-perfect playback including DSD, native and DoP); [ADR 0006](../adr/0006-native-dsd-through-upstream-driver-work.md) (native DSD through upstream driver work).
- **Sources:** [CS43198 spec sheet](https://github.com/opendap-project/parts-lib/blob/main/Cirrus-Logic/CS43198-CNZR.md) (DS1156F2), the mainline `cs43130` driver, board ADR 0001 (Cirrus DAC family) and ADR 0010 (master clocks).

## 1. The constraint

DSD512 is a 1-bit stream at 512 × 44.1 kHz = 22.5792 MHz per channel.

| Path into the CS43198 | Limit | Source |
|---|---|---|
| Native DSD input (DSDCLK, DSDA, DSDB) | DSD64, DSD128, DSD256. DSDCLK at most fMCLK_INT / 2 = 11.2896 MHz | DS1156F2 Table 3-19 |
| DoP over the PCM port (ASP) | PCM at most 384 kHz, so DoP reaches DSD128 (352.8 kHz); DSD256 over DoP would need 705.6 kHz | DS1156F2 p. 2, Table 3-18 |
| Mainline driver today | A native DSD DAI (`cs43130-xsp-dsd`) and two DoP DAIs exist, all constrained to 176.4 and 352.8 kHz (DSD64, DSD128). The DSD speed field mask is one bit wide, so DSD256 cannot be selected (§5.1) | `cs43130` driver, v7.3 |

**The on-board DAC cannot play DSD512 natively, in any mode.** This is the chip, not the driver. Every DAC in the Cirrus family the board uses (ADR 0001) shares the DSD256 ceiling, as far as the datasheets read so far show (**UNVERIFIED** for every family member other than the CS43198).

## 2. Proposal: three tiers, each stated honestly

> **Revised 2026-10-22 after the §5 findings:** the RK3566 I2S-TDM block is specified up to 192 kHz frame rate (RK3568 TRM p. 698; mainline driver rates 8–192 kHz). On-board PCM is bit-perfect up to 192 kHz; DoP on-board reaches DSD64 only (DSD128 DoP needs 352.8 kHz); native DSD up to DSD256 is unaffected (176.4 kHz frames). Tier B therefore converts to 176.4 kHz by default. If the first prototype shows the block running cleanly at 352.8 kHz, that limit is revisited.

| Tier | Formats | How | Bit-perfect |
|---|---|---|---|
| **A. Native, on-board** | DSD64, DSD128, **DSD256** | Native DSD through the CS43198's dedicated DSD pins, fed by the SoC's I2S-TDM block (ADR 0006 work, extended from DSD128 to DSD256). The board already routes DSD on its own nets (board pin plan, cross-validation F28), and DSDCLK 11.2896 MHz comes from the 22.5792 MHz MCLK (ADR 0010) | Yes |
| **B. Converted, on-board** | **DSD512** (and DSD1024 files, if they appear) | The playback engine converts DSD512 in software to PCM 176.4 kHz / 32-bit (default; the SoC's I2S block is specified up to 192 kHz, §5), or to DSD256 (option; an open-source sigma-delta modulator with DSD256 noise-shaping filters exists, §5.3, but its quality for this use is **UNVERIFIED**), and plays that natively | No, and labelled so in the UI ("DSD512 → PCM 176.4 kHz") |
| **C. Native, external** | **DSD512** and above | The T1 as USB host on the main USB-C streams native DSD to a USB DAC that supports it (ALSA `snd-usb-audio` native DSD formats, per-device quirks), DoP as fallback | Yes |

### Why this split

- It keeps the promise exact: the T1 never claims native DSD512 on its own outputs, because the hardware cannot do it, and it never hides a conversion (OS-020 and the voice rule "engineering before promises").
- Tier A covers the DSD rates the on-board DAC supports, at their full native quality.
- Tier B lets every DSD512 file play on the headphone outputs. Converting DSD to high-rate PCM is the established path for DACs without DSD512 support. The RK3566's four Cortex-A55 cores with NEON have capacity for one stereo DSD512 decimation stream; the battery cost is to be measured (**UNVERIFIED**).
- Tier C gives native DSD512 to users who own a DAC that supports it, with no compromise.

### What it does not do

Native DSD512 on the on-board outputs would require a different DAC family. That reopens board ADR 0001 (Cirrus, confirmed by the maintainers), the clocking (ADR 0010), the analog stage and the power budget, for one format. This proposal does not recommend it for the T1.

## 3. Work items

1. **Driver, DAC side** (`sound/soc/codecs/cs43130.c`, upstream, ADR 0006). The native DSD DAI already exists (§5.1); the patch series extends it:
   1. Fix `CS43130_DSD_SPEED_MASK` from `0x04` to `0x0C` (DSD_SPEED is bits 3:2, DS1156F2 p. 109). Without it, DSD256 cannot be written.
   2. Give the XSP DSD DAI its own startup constraint and derive the DSD rate from `params_rate() × params_physical_width()`, as `ak4458.c` does, instead of matching 176.4 / 352.8 kHz. Map 2.8224 / 5.6448 / 11.2896 Mbit/s (and the 48 kHz family) to DSD_SPEED 00 / 01 / 10; reject DSD256 with Direct DSD mode and with phase modulation (p. 108–109).
   3. Add `DSD_U8`, `DSD_U16_LE/BE` and `DSD_U32_LE/BE` to that DAI so it can pair with a CPU DAI that streams 32-bit words.
   4. Expose the DSD processor controls the driver leaves at reset values: DSD_ZERODB, DSD_HPF_EN, DSD_SWAP_CHAN, DSD_COPY_CHAN, DSD_INV_A/B (register 0x70006, p. 110). Dual mono needs COPY_CHAN and INV_B per device (DS1156F2 Ex. 5-9, p. 77).
   5. Wait for the DSD soft-mute ramp before power-down on the CS43198 path, as the CS43130 path already does (130 ms), or confirm on hardware that no wait is needed.
   6. With the clocking proposed in item 3, keep the ASP clock generator of the clock-master DAC running (SCLK1 = DSD bit rate, LRCK1 = DSD bit rate / 64) while the DSD DAI plays, and set DSD_M/SB = 0 on both devices. Today the ASP is powered only by the PCM and DoP DAPM paths.
2. **Driver, SoC side** (`sound/soc/rockchip/rockchip_i2s_tdm.c`, upstream, ADR 0006). The I2S1 block can carry a continuous DSD bitstream per SDO line in I2S mode with 32-bit words and 64-bit frames, at frame rates up to 176.4 kHz for DSD256, inside the TRM's 192 kHz limit (§5.2). It has no DSD or PDM mode, and its channel select counts in pairs (two, four, six or eight channels). The patch series:
   1. Accept `DSD_U32_LE` (and `DSD_U16_LE` with VDW 16) in `rockchip_i2s_tdm_init_dai()` and `hw_params`, with VDW 32, MSB first, I2S format; extend `.rates` so that the ALSA rate of DSD_U32 (DSD256 = 352.8 kHz) passes.
   2. For DSD, program one channel per SDO line: two DSD channels → four I2S slots on two paths, LRCK = ALSA rate / 2, bit clock = ALSA rate × 32.
   3. Allow a per-stream TX path map (or a second `rockchip,i2s-tx-route` for DSD), so that PCM uses SDO0 and DSD uses the reserved lines.
   4. Measure the hardware's channel-to-line order. If channels are paired per line (ch0/ch1 on SDO0), the DSD frame needs a fixed word permutation, which is not standard ALSA DSD semantics and may block upstreaming (**UNVERIFIED**).
   5. A machine driver (modelled on `imx-card.c`, which switches the link to `SND_SOC_DAIFMT_PDM` for DSD formats) that binds the I2S1 TX DAI to the ASP PCM DAIs and the XSP DSD DAIs of both CS43198s.
3. **Board handoff** (no change made here; for the board repository). DSDCLK of both DACs must carry the I2S1 TX bit clock (SCLKTX net), because the I2S block launches every SDO line on SCLKTX. Proposed clocking: DAC L stays ASP clock master in DSD mode at frame rate = DSD rate / 64, and both DSD interfaces run as slaves on that clock (DS1156F2 p. 47, p. 49). Option to evaluate: DSD left on SDO0 (already wired to DAC L) and DSD right on SDO1, which needs four I2S channels instead of six and no path remap.
4. **Playback engine:** DSD512 → PCM conversion as a selectable, visible mode, implemented in the engine (Rust) as two decimation stages: a 1-bit lookup-table FIR at the DSD rate (÷8), then a polyphase float FIR to the output rate. Reference implementations for the verification vectors: MPD (dsd2pcm + libsoxr) and dsd2dxd (§5.3). The filter is documented (passband, stopband, ultrasonic rejection above the output Nyquist) and its output verified against captured samples (TK-012). The output rate depends on risk R1 (§5.5): 352.8 kHz if the I2S block is verified at that rate, otherwise 176.4 kHz.
5. **USB host DSD:** native `DSD_U32_BE` / `DSD_U32_LE` / `DSD_U16` / `DSD_U8` through `snd-usb-audio` with no kernel change for listed devices; `quirk_flags` bit 15 (`dsd_raw`) for unlisted UAC2 devices that advertise raw data; DoP in the engine as fallback; a compatibility list built from tests (§5.4).
6. **Verification:** bit-exact capture of tiers A and C (on-board through the RP2354A I2S/DSD tap, BRD-040/041; USB with a capture-capable DAC or the virtual T1); tier B checked for correctness of the conversion, not for bit-perfection. The first hardware test for tier A: play a known four-channel 32-bit pattern and capture SDO0–SDO2 to settle the line order (item 2.4).

## 4. Decision needed

- Accept the three tiers as the DSD512 answer for the T1 (recommended), or reopen the DAC family for native on-board DSD512.
- If accepted: OS-020 is restated as "bit-perfect up to DSD256 on-board and up to the external DAC's limit over USB; higher DSD rates on-board are converted and labelled", and ADR 0006 is extended from DSD128 to DSD256.

**Mainline driver (v7.3, `sound/soc/codecs/cs43130.c`, `cs43130.h`).**

- Four DAIs: `cs43130-asp-pcm`, `cs43130-asp-dop`, `cs43130-xsp-dop` and **`cs43130-xsp-dsd`** (lines 1638–1688). The last is a native DSD DAI on the DSD interface: its `hw_params` sets DSD_M/SB from the link's clock role, DSD_SPEED and DSD_PRC_SRC = DSD interface (lines 813–871). The earlier statement in §1 and in the system architecture research that the driver has "no native DSD" was wrong; it is corrected above.
- Its formats are `CS43130_DOP_FORMATS` = `DSD_U16_LE`, `DSD_U16_BE`, `S24_LE` (`cs43130.h` lines 288–290). Its startup reuses the DoP rate list {176400, 352800} (lines 1496–1511, 1628–1633): DSD_U16 at 176.4 kHz is DSD64, at 352.8 kHz DSD128. Any other rate returns `-EINVAL` (lines 843–853).
- `CS43130_DSD_SPEED_MASK` is `0x04` (`cs43130.h` line 306), one bit of the two-bit DSD_SPEED field. Writing 256·Fs (`0b10 << 2`) through this mask writes 0, i.e. DSD64. **DSD256 needs a mask fix, not only a new rate.**
- Controls: "Master DSD Playback Volume" (DSD_VOLUME_A/B, line 1118) and "DSD Phase Modulation" (line 1128). DSD_ZERODB, DSD_HPF_EN, SWAP/COPY/INV and DIR_DSD are not exposed; they stay at reset values.
- MCLK: for the first active DAI the driver selects 22.5792 MHz if it divides by the rate, else 24.576 MHz, then uses the external MCLK (`pll_bypass`) or the PLL (lines 825–841).
- DAPM: "XSPIN DSD" powers PDN_DSDIF and routes to the "DSD" widget (DSD_EN) and "HiFi DAC" (PDN_HP) (lines 1438–1468). For the CS43198 the DAC event writes the pop-free pair 0x10010 = 0x99 / 0x80032 = 0x20, waits 12 ms after power-up and clears 0x80032 (lines 1309–1350), matching Ex. 5-4. On stream stop it sets DSD_MUTE_A/B with no wait on the CS43198 path, where the CS43130/CS4399 path waits 130 ms (lines 1210–1233).
- **CS43130 versus CS43198 in the driver:** the CS43130 and CS4399 get extra hidden-register sequences around DSD and PCM power events (`dsd_seq`, `pcm_seq`, `mute_seq`, `unmute_seq`, lines 1131–1181); the CS43131 and CS43198 do not. The CS43198 registers the "digital" component (no headphone-load measurement widgets; lines 2612–2618). The "PCM Ch Select" control writes a hidden-register sequence for the CS43131/CS43198 (lines 1012–1086) that differs from the CS43198 mono sequence in DS1156F2 §5.11 (p. 64); whether it is correct for the CS43198 is **UNVERIFIED**.

**What a DSD256 native DAI needs** is listed in §3 item 1. Native DSD64 and DSD128 work in the driver today only with a CPU DAI that offers `DSD_U16`; DSD256 needs the mask fix and a rate or bit-rate based speed selection.

### 5.2 RK3566 I2S-TDM raw DSD streaming

**Hardware (RK3568 TRM Part 1, chapter 21; I2S1 is the same block on the RK3566, compatible `rockchip,rk3568-i2s-tdm` in `rk356x-base.dtsi`).**

- I2S1 supports I2S, PCM and TDM modes, 8 channels in I2S mode, "up to 192kHz sample rate", 16 to 32-bit data, MSB or LSB first, four 32-bit × 32 TX FIFOs, separate TX and RX LRCK (p. 698).
- TXCR: `TX_PATH_SEL` maps path 0–3 to SDO0–SDO3, "when TDM mode, only path0 enable"; `CSR` selects two, four, six or eight channels; `VDW` 16–32 bits; `TFS` I2S, PCM, TDM-PCM, TDM-I2S (pp. 705–707). There is **no DSD or PDM mode** and no one-channel-per-line mode.
- In I2S mode with VDW = 32 and a 64-bit frame, every bit clock on an SDO line carries a data bit: the line is a continuous 1-bit stream, and LRCK is ignored by the DAC in DSD mode. For DSD256 the bit clock is 11.2896 MHz and the frame rate 176.4 kHz, inside the 192 kHz limit (computed). DSD64 and DSD128 run at 44.1 and 88.2 kHz frames.
- Every SDO line is launched on the one TX bit clock (SCLKTX). The DSD clock at the DAC must therefore be SCLKTX, not a separate clock (§3 item 3).
- The TRM does not state, for I2S mode with four or more channels, which channels go to which line; the driver and the vendor code treat lines as stereo pairs. **UNVERIFIED** until measured (§3 item 6).

**Mainline driver (v7.3, `sound/soc/rockchip/rockchip_i2s_tdm.c`).**

- Formats: `S8`, `S16_LE`, `S20_3LE`, `S24_LE`, `S32_LE` (lines 1050–1052); `hw_params` rejects anything else (lines 687–705). Channels 2, 4, 6, 8 (lines 707–722); `channels_min = 2` (line 1069).
- Rates: `SNDRV_PCM_RATE_8000_192000` (line 1071). The CS43198 DAIs use `SNDRV_PCM_RATE_KNOT`, so ASoC takes the CPU mask and limits the card to 192 kHz (`snd_pcm_rate_mask_intersect`, `sound/core/pcm_misc.c` lines 554–569; `soc_pcm_hw_update_rate`, `sound/soc/soc-pcm.c` lines 706–717). **Consequence (risk R1):** on stock mainline the on-board card cannot open PCM at 352.8 or 384 kHz, nor DoP DSD128 (352.8 kHz frames); only DoP DSD64 at 176.4 kHz. The system architecture research assumed DoP DSD128 on-board.
- Clock roles: provider (`BP_FP`) and consumer (`BC_FC`) (lines 360–371); `set_bclk_ratio` 32–512 (lines 816–827); static TX/RX line routing from `rockchip,i2s-tx-route` / `rockchip,i2s-rx-route` at probe (lines 1163–1213). `rockchip,io-multiplex` only shares SDO1–3/SDI1–3 balls between TX and RX through the GRF and checks channel counts (lines 517–579); it is irrelevant on the M1 pins, where the lines are separate.
- **Rockchip vendor kernel:** no `DSD` occurrence in `rockchip_i2s_tdm.c`, `rockchip_sai.c` or `rockchip_i2s.c` on `develop-5.10`, `develop-6.1` or `develop-6.6`. The vendor I2S-TDM driver declares `SNDRV_PCM_RATE_CONTINUOUS` and adds a multi-lane TDM mode (`rockchip,tdm-multi-lanes`) that still pairs channels per line. There is no Rockchip DSD code to port.

**Models in mainline for native DSD on an SoC port.**

- NXP: `fsl_sai.h` lists `DSD_U8`, `DSD_U16_LE`, `DSD_U32_LE` (lines 13–19). `fsl_sai.c` treats `SND_SOC_DAIFMT_PDM` as DSD mode: one channel per data line (`pins = channels`, lines 640–643) and a pinctrl state "dsd512" when the bit clock reaches 22.5792 MHz (lines 108–129). `imx-card.c` switches the link to `SND_SOC_DAIFMT_PDM`, one slot of the format's width, when the stream format is DSD (lines 244–258, 340–347), and sets MCLK to 22.5792 or 24.576 MHz for DSD (lines 393–398). `ak4458.c` derives the DSD rate from `rate × physical width` (line 366) and rejects DSD512 on that codec (line 385).
- Amlogic (`axg-tdm-*`), Allwinner (`sun4i-i2s.c`), STM32 SAI and MediaTek MT8195 ETDM: no DSD support found in the files read.

**Conclusion.** Native DSD64–DSD256 on I2S1 is feasible in hardware as a continuous 32-bit-word stream per SDO line, at standard I2S frame rates up to 176.4 kHz, with the DSD clock taken from SCLKTX. The patch outline is §3 item 2. Two open points decide how clean it is: the channel-to-line order (a fixed word permutation may be needed, which conflicts with standard ALSA DSD channel semantics and may complicate upstreaming), and the clocking topology on the board (§3 item 3).

### 5.3 DSD512 to PCM, and DSD512 to DSD256

|---|---|---|---|

For DSD512 that is 2.8224 MHz; MPD then resamples to the output rate (libsoxr) | Designed for DSD64: "flat response up to 48 kHz", "below 70 kHz practically alias-free" after ÷8, "stopband rejection about 160 dB" (source comment) | BSD-2-Clause for dsd2pcm; MPD GPL-2.0-or-later; libsoxr LGPL-2.1-or-later |

Frequency response of the dsd2pcm filter (computed from the 48 published half-taps, at fs = 64 × 44.1 kHz): −0.1 dB at 59.7 kHz, −3 dB at 120.7 kHz, −15.4 dB at 176.4 kHz, −116.4 dB at 282.24 kHz, −152.6 dB at 352.8 kHz. Applied to DSD512 every frequency scales by 8 (−3 dB near 966 kHz). The filter is therefore only a first decimation stage for DSD512: ultrasonic modulator noise between the output Nyquist frequency and about 1 MHz must be removed by the second stage. MPD's DSD512 path quality is set by its resampler, not by dsd2pcm.

**CPU estimate, one stereo DSD512 stream to 352.8 kHz on Cortex-A55** (estimate; 1.8 GHz assumed; not measured):

- Stage 1, 1-bit lookup FIR at 22.5792 MHz, ÷8 to 2.8224 MHz: 96–128 taps = 12–16 table lookups and adds per output, 2 × 2.8224 M outputs/s → 68–90 M lookup-adds/s, about 140–180 M cycles/s at 2 cycles each.
- Stage 2, polyphase float FIR ÷8 to 352.8 kHz, passband to about 100 kHz, stopband from 176.4 kHz at 120 dB: about 290 taps (Kaiser estimate) → 2 × 352.8 k × 290 ≈ 205 M MAC/s, about 100–200 M cycles/s at 1–2 MAC per cycle with NEON.
- Total about 250–380 M cycles/s, **roughly 15–20 % of one A55 core**. A 64-bit float implementation (as dsd2dxd) costs about twice that. The battery cost stays **UNVERIFIED** until measured.

**DSD512 → DSD256 modulator.** SoX (and its maintained fork sox_ng, release 14.8.1 of 2026-08-29) has an `sdm` effect by Måns Rullgård: a 1-bit sigma-delta modulator with CLANS and standard noise-shaping filters of order 4 to 8, tabulated for 64, 128 and **256** × 44.1 kHz, with an optional partial trellis search (order ≤ 32, paths ≤ 32, latency ≤ 2048). Licence LGPL-2.1-or-later (`src/sdm.c` header). Its manual warns that trellis results "can include high noise levels or instability". No published measurement of its noise floor or stability at DSD256 was found, so "adequate quality" stays **UNVERIFIED**. ### 5.4 USB host native DSD

- **Formats.** UAC has no DSD format bit. `snd-usb-audio` sets `fp->dsd_raw` when a UAC2 altsetting advertises `UAC2_FORMAT_TYPE_I_RAW_DATA` (`sound/usb/format.c` lines 58–66) and asks `snd_usb_interface_dsd_format_quirks()` which DSD format to expose; if one is returned, it replaces the PCM formats of that altsetting (format.c lines 158–160).
- **Quirk tables** (`sound/usb/quirks.c` lines 2010–2109): Playback Designs (DoP, `DSD_U8`, `DSD_U16_LE` with bit reversal); per-device XMOS altsetting 2 and altsetting 3 lists (`DSD_U32_BE`); Amanero Combo384 by firmware (`DSD_U32_LE` or `_BE`); `QUIRK_FLAG_ITF_USB_DSD_DAC` devices (TEAC, Esoteric, Denon, Marantz, Luxman; last altsetting is native DSD); and the generic `QUIRK_FLAG_DSD_RAW` path (`DSD_U32_BE` on raw-data altsettings). Vendor-wide `DSD_RAW` entries (lines 2598–2645) cover AURALiC, Thesycon-based devices, iBasso, XMOS-based devices, Accuphase, Oppo, Mytek, IAG, Musical Fidelity, Rotel, Gustard/ESS-based, FiiO, T+A, McIntosh, Cayin, Comture, HEM, Khadas, MSB, EVGA and HiBy; device entries add others (iBasso DC04 Ultra, SMSL, ddHiFi TC44C, HiBy FC4, among others).
- **Unlisted devices:** the `quirk_flags` module parameter, bit 15 (`dsd_raw`), enables the generic raw-DSD path without a kernel change (`Documentation/sound/alsa-configuration.rst` lines 2299–2354).
- **DoP:** done in user space for almost all devices (MPD `dop` option); the kernel inserts DoP markers itself only for altsettings flagged `dsd_dop` (Playback Designs; `sound/usb/pcm.c` lines 1399–1454).
- **DSD512 support** is not a driver property: the rate comes from the device's descriptors (DSD512 as `DSD_U32_BE` is 705.6 kHz). Which DAC models reach DSD512 is **UNVERIFIED** per device and belongs to the compatibility list.
- **USB 2.0 bandwidth.** A high-speed isochronous transaction carries at most 1024 bytes, with up to two extra transactions per microframe (`drivers/usb/core/config.c` lines 215–221, 465–486); `snd-usb-audio` sizes packets with `usb_endpoint_max_periodic_payload()`, which includes them (`sound/usb/stream.c` line 706). Native DSD512 stereo is 5.6448 MB/s = 705.6 bytes per 125 µs microframe: one transaction (computed). DSD1024 is 1411.2 bytes and needs a high-bandwidth endpoint. DoP DSD512 needs 1.4112 MHz PCM, 1058–1411 bytes per microframe with 3- or 4-byte subslots, so also a high-bandwidth endpoint, and a DAC that accepts that rate. A full-speed device (1023 bytes per 1 ms frame) cannot carry DSD512. Whether the RK3566 USB host controller handles high-bandwidth isochronous endpoints reliably is **UNVERIFIED**.

### 5.5 Risks that could change the plan

- **R1, 192 kHz on the I2S block.** The TRM states 192 kHz, and mainline declares 8–192 kHz. Tier B's default output (PCM 352.8 kHz) and on-board DoP DSD128 depend on running I2S1 above that. Native DSD256 does not (176.4 kHz frames). If 352.8 kHz cannot be verified on hardware, tier B's default output becomes PCM 176.4 kHz (or DSD256 through a modulator), and on-board DoP stops at DSD64. This is a maintainer decision once measured.
- **R2, channel-to-line order.** If I2S1 pairs channels per SDO line, native DSD needs a word permutation that standard ALSA DSD formats do not express; upstream acceptance is uncertain.
- **R3, board clocking.** DSDCLK must be the SCLKTX net; the pin plan's "own net" wording needs to say so before layout.
